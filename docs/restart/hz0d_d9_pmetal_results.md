# HZ-0D D9: PMetal Implementation

Date: 2026-08-04. Real evidence for D9's plan text: "Apply/update/
decay/snapshot/rollback/reset and batched deterministic sessions."
Staged exactly like HZ-0B's own B10 precedent
(`docs/restart/hz0b_b10_pmetal_design.md`): a real, complete, tested
Rust CPU-tensor port first, a Python `ctypes` bridge on top of it, and
an explicit, benchmark-backed decision on whether a Metal GPU tier is
warranted yet -- not built reflexively just because HZ-0A/HZ-0C have
one.

## What's built

- `restart/hz0a_pmetal/crates/hz0d-pmetal-fastweights/` --
  `#![forbid(unsafe_code)]`, zero production dependencies, matching
  `hz0b-pmetal-memory`'s own conventions. Ports every op D1's contract
  names: `reset`, `apply` (`apply_fast_linear`), `update`
  (`update_fast_weights`), `decay` (`decay_fast_weights`), `snapshot`,
  `rollback`, plus `effective_delta` and `fast_state_memory_bytes`.
- `restart/hz0a_pmetal/crates/hz0d-pmetal-fastweights-bridge/` -- a
  plain `cdylib` + `extern "C"` FFI boundary, no PyO3/maturin, matching
  `hz0b-pmetal-memory-bridge`'s own established pattern in this
  workspace.
- `restart/hz0a_pmetal/python/hz0d_fastweights_bridge.py` -- numpy-backed
  `ctypes` wrapper.
- `scripts/hz0d_generate_rust_parity_fixture.py`,
  `restart/hz0a_pmetal/crates/hz0d-pmetal-fastweights/tests/{parity,correctness}.rs`,
  `tests/reference/test_hz0d_pmetal_bridge.py` -- 8 Rust correctness
  tests, 1 Rust cross-language parity test, 3 Python bridge tests (12
  total, all real, all passing).

## New relative to the Python reference: an explicit session (batch) axis

`reference/hz0d_fast_weights.py::FastWeightState` has no batch
dimension -- it is one session's state. D9's plan text names "batched
deterministic sessions" as a real, separate requirement (many users'
independent, isolated sessions processed together, sharing the SAME
frozen backbone but never leaking state between each other). This crate
adds that dimension for real, not just in the type signature:

- `batched_update_touches_only_the_named_session`: updating session 1
  of a 3-session batch leaves sessions 0 and 2 BIT-IDENTICAL to their
  pre-update values (`assert_eq!`, not approximate), and only session
  1's `update_count` increments.
- `apply_is_deterministic_and_independent_per_session_in_one_batched_call`:
  the same batched `apply()` call run twice gives bit-identical output;
  two sessions with deliberately different fast-weight deltas but the
  same input magnitude pattern produce genuinely different outputs
  (proving the delta really is session-specific, not silently shared).
- The parity test (`replays_two_independent_sessions_batched_and_matches_python_exactly`)
  replays TWO independently-generated Python traces through ONE
  `sessions=2` Rust state and confirms each session's final state
  matches its own trace exactly -- cross-language correctness AND
  batch-independence, checked together.

## RNG: generated by Python/MLX, not reimplemented in Rust

`init_fast_weights`'s asymmetric init draws `a_fast` from
`mx.random.normal`. Replicating MLX's PRNG algorithm bit-for-bit in
Rust would be real, unrewarded work -- nothing downstream needs Rust to
independently generate that first draw. Matching every other manual
state-machine port in this project, `reset` takes a caller-supplied
`a_fast_init` buffer (real MLX randomness, generated once by Python)
and constructs `b_fast` as the exact zeros the asymmetric-init contract
requires -- that IS the real, deterministic part of reset, and it is
what's ported. Verified directly:
`reset_gives_exactly_zero_realized_delta_asymmetric_init`.

## Real bug found and fixed the same day: `apply()`'s avoidable dense-delta materialization

Direct benchmarking (matching C8's own discipline: measure before
claiming a kernel is efficient) at the D1 contract's real scale
(`dim=768`, `rank=16`) found `apply()`'s first implementation cost
`755.7us/call` for a single session -- because it called
`effective_delta` (materializing the full dense `[768, 768]` delta,
`dim * dim * rank ≈ 9.4M` multiply-adds) before applying it, instead of
using the mathematically identical low-rank-aware form
`x @ (A @ B).T == (x @ B.T) @ A.T` (`2 * dim * rank ≈ 25K` multiply-adds
for the same result). Fixed by computing the low-rank contribution
directly, without ever materializing the dense delta:

```
apply() BEFORE fix: 755.7us/call (1 session, dim=768)
apply() AFTER fix:  244.3us/call (1 session, dim=768)  -- 3.1x faster
```

The fix is verified CORRECT, not just faster: every Rust correctness
test and the cross-language parity test (which checks `apply()`'s exact
numeric output against the real Python reference) still pass unchanged
after the fix -- `x @ (A@B).T` and `(x @ B.T) @ A.T` are the same
computation to floating-point precision, confirmed directly rather than
assumed from the algebra. The remaining `244.3us` is now dominated by
the IRREDUCIBLE dense `base_weight` matmul (`dim * dim ≈ 590K`
multiply-adds, the same cost any plain linear layer forward would pay
regardless of fast weights) -- the fast-weight-specific overhead is now
genuinely small, matching what a low-rank adapter should cost.

Batched-session throughput scales linearly with session count in this
naive per-session loop (`235.5us/session` at 64 batched sessions, close
to the single-session `244.3us`) -- no cross-session vectorization is
attempted at the CPU-tensor tier, an honest, disclosed limitation
matching this tier's own scope (a correct reference, not yet a
throughput-optimized kernel).

## GPU tier: not built this pass, justified the same way B10 was

At the fixed cost above, 6 anchor-attention layers' worth of fast-weight
`apply` calls cost `~1.5ms` per token (`6 * 244.3us`) against a real,
measured full-model forward pass of `~18.5-19.2ms`
(`docs/restart/hz0c_c9_end_to_end_report_results.md`) -- under `8%`
overhead, and this Rust CPU-tensor tier is not even the current
production integration path (`reference/hz0d_d6_integration.py`'s real
MLX-native wiring is, and MLX's own compiled `matmul` is not what this
crate measures). Building a Metal GPU kernel for an operation that is
already a small fraction of the real per-token cost, with no current
caller needing it, would repeat B10's own explicitly-named mistake
pattern ("built reflexively" rather than because there's a real,
measured reason) -- so it is deferred here, backed by a real benchmark
rather than an a priori argument, exactly matching
`docs/restart/hz0b_b10_pmetal_design.md`'s own precedent and reasoning.

## Exit gate check

"Apply/update/decay/snapshot/rollback/reset and batched deterministic
sessions": all 6 named contract operations are real, tested, Rust code
(not stubs), verified both internally (correctness tests) and against
the real Python reference (parity tests, both Rust-native and through
the full Python<->ctypes<->Rust<->ctypes<->Python round trip). Batched
deterministic sessions are a genuinely new capability beyond the Python
reference, verified independent (no cross-session leakage, bit-exact)
and deterministic (identical repeated calls produce identical output).
A real performance bug was found and fixed along the way (3.1x), with
the fix verified correct via the same parity tests, not assumed safe.
