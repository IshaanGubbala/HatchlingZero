## Backward Kernel Fusion: Eliminate (B,S,H,V,K) Partial-Gradient Buffers (2026-07-28)

- **Problem identified by the forward/backward/optimizer profiling diagnostic** (`scripts/hz0a_profile_training_step.py`): hybrid's backward pass was disproportionately slow versus forward relative to the transformer baseline (forward 1.6x slower, backward 2.5x slower), even with the native Metal kernel already in use. Root cause: `native_gdn2_backward`'s Metal kernel materializes four full `(batch, steps, heads, value_dim, key_dim)` intermediate tensors (`grad_q_partial`, `grad_k_partial`, `grad_d_partial`, `grad_e_partial`) — one thread per `(batch, head, value)`, each writing its own value-slice — then reduces them over the value axis with four separate `mx.sum(..., axis=3)` calls. At the locked config (B=8, S=128, H=12, V=K=64) that's `8*128*12*64*64*4 bytes ≈ 1.34GB` per buffer, `≈5.37GB` total per backward call, of which only `≈100MB` (the post-reduction `(B,S,H,K)` shape) is actually needed — a `~53x` padding blowup, explaining the elevated cache-memory numbers seen throughout this session's profiling.
- **First attempt (rejected at the time): Metal atomic float accumulation.** `mx.fast.metal_kernel(..., atomic_outputs=True)` is a real, documented MLX option that would let every value-thread `atomic_fetch_add_explicit` directly into a shared `(B,S,H,K)` buffer, no intermediate padding at all. Verified via isolated smoke test that `atomic_store_explicit` compiles and runs correctly on this hardware (Apple M5 Max, MLX 0.29.3) — but `atomic_fetch_add_explicit` on a float buffer fails to even compile, every time, including a single-thread/single-call reproduction: `RuntimeError: [metal::Device] Unable to load kernel ... Compilation failed due to an interrupted connection: XPC_ERROR_CONNECTION_INTERRUPTED`. At the time this was written up as "a real limitation of this MLX/Metal combination for float atomic add specifically (store works, fetch-add doesn't)" -- **that framing was wrong and is corrected here (2026-07-29):** the exact same `atomic_fetch_add_explicit` on `device atomic<float>*`, both `device atomic<float>*` and `device atomic_float*` spellings, single-thread and 256-concurrent-thread cases, compiles and runs perfectly via a raw Metal dispatch bypassing MLX entirely (the `metal` Rust crate already used by `hz0a-pmetal-gpu`) -- exact correct results (`1.0`, `256.0`) every time. Re-tested `mx.fast.metal_kernel(..., atomic_outputs=True)` directly against this same operation afterward and got the identical `XPC_ERROR_CONNECTION_INTERRUPTED` again, with or without an explicit cast, while `atomic_store_explicit` through the same MLX path still works. **Precise, now-correct characterization: this is a bug or limitation specific to MLX 0.29.3's `mx.fast.metal_kernel` JIT-compilation pipeline for `atomic_outputs=True` kernels using `atomic_fetch_add_explicit` -- not a hardware limitation, not a fundamental Metal Shading Language limitation, and not present in raw/direct Metal dispatch.** Practical consequence for this project is unchanged (the threadgroup-memory reduction fix already shipped and works well, and `hz0a-pmetal-gpu`'s raw dispatch could use real atomics if ever wanted), but the causal claim in the original write-up was too broad and is corrected for the record.
- **Fix shipped: `native_gdn2_backward_fused`** in `reference/hz0a_mlx_metal.py`, alongside a new `_BACKWARD_BODY_FUSED` Metal source. Restructured the dispatch from `B*H*V` independent threads to `B*H` threadgroups of `V` threads each (`threadgroup_position_in_grid` = batch*head, `thread_position_in_threadgroup` = value channel). Each thread still runs the identical per-value state recurrence (unchanged math, unchanged finite-difference-verified forward/backward derivation), but instead of writing its per-value partial gradient to a padded global buffer, it writes into a `threadgroup float shared_buf[64][64]` scratch array, synchronizes with `threadgroup_barrier`, and one pass over `K` threads sums down each column to produce the final `(B,S,H,K)`-shaped gradient directly -- reused sequentially for `grad_q`, `grad_k`, `grad_d`, `grad_e` (4 barrier-pairs per timestep, 16KB shared memory, well within Apple Silicon's per-threadgroup limit). Requires `value_dim == key_dim`, true for the locked A1 spec (both `64`); the original `native_gdn2_backward` is kept byte-for-byte unchanged as the correctness baseline and as an automatic fallback in `_native_gdn2_vjp` for any future config where the dims differ.
- **Parity: `tests/reference/test_hz0a_mlx_metal_fused_backward.py`**, 4 new tests, all passing at the existing `atol=2e-5, rtol=2e-5` tolerance: small mismatched shape, the real locked shape (`V=K=64`), an uneven/non-power-of-two sequence length (37), and a rejection test for `value_dim != key_dim`. Full suite: 103/103 passing (99 prior + 4 new).
- **Isolated backward-kernel benchmark** (same process, back-to-back, B=8/S=128/H=12/K=V=64, the real per-chunk training shape): baseline `7.49ms/call`, fused `3.89ms/call` -- **1.93x speedup (48% reduction)**, exceeding the 30% target. Peak memory per call: `0.851GB -> 0.066GB` (**92% reduction**). Max absolute gradient error vs baseline across all 7 outputs: `<= 1.9e-5`, within tolerance; the higher relative-error numbers reported alongside it are near-zero-denominator artifacts on values close to zero, not a real discrepancy.
- **Full-model, same-process, same-warmup comparison** (forward+backward, real hybrid model, monkey-patching the VJP to isolate old-vs-new with no cross-process system-noise confound): `648.5ms -> 438.2ms` (**1.48x**), real training throughput `2,506 -> 3,410 tok/s` (**1.36x**), peak memory `12.77GB -> 10.76GB` (-16%), cache memory `11.44GB -> 8.42GB` (-26%). Smaller than the isolated 1.93x because backward is only part of the full step (RMSNorm/projections/MLP/embeddings/attention layers are unaffected by this change) -- exactly as the profiling diagnostic predicted before this fix was attempted.
- **Dispatch count**: baseline issues 1 Metal kernel dispatch plus 4 separate `mx.sum` reduction dispatches (5 total GPU dispatches per backward call); fused issues 1 dispatch total (the value-axis reduction happens inside the kernel via threadgroup barriers, no follow-on MLX ops needed).
- `native_gdn2_backward_fused` is now the **default** backward path (wired into `_native_gdn2_vjp`), used automatically by both the hybrid and any future kernel-backed model at the locked shape. No model architecture or training semantics changed -- same math, same gate parameterization, same chunk/state-carry behavior, only how the value-axis reduction is computed.
- **Not done in this pass**: forward-path fusion of the surrounding RMSNorm/QKV/gate projections around the recurrence kernel (still separate MLX ops per the earlier profiling breakdown's hypothesis #3), and `mx.compile`-ing the full training step -- both remain real, identified, unexplored follow-up work.

## Truncated-BPTT State-Carry Bug: Found and Fixed (2026-07-28)

- **What it was:** `hz0a_native_stage_runner.py`'s `truncate_backward` loop ran two forward passes per chunk -- a throwaway `model(chunk, states)` just to get the post-chunk state, then a separate `chunk_value_and_grad(model, chunk, states)` for the real loss/gradient. By the second call, `states` had already been overwritten with *this chunk's own ending state*, not the correct previous-chunk carry-in. Every chunk's loss and gradients were computed against a self-referential, wrong recurrent state.
- **Confirmed empirically, not just by reading code:** a standalone repro on a tiny 2-layer GDN2 model showed the production pattern's chunk1 loss (carry = chunk1's own ending state) came out to `3.578744888305664`, versus the correct carry-in (chunk0's real ending state) giving `3.601097822189331` -- a real, nonzero, reproducible difference.
- **Asymmetric impact -- this is not a "redo everything" finding:**
  - **Transformer: zero correctness impact, performance-only.** Default `carry_attention_state=False` resets attention state to `None` every chunk regardless of the bug (attention state is a tuple, so it's always reset), so both the buggy and correct carry-in were identically `None` for every transformer run. The bug only cost transformer one wasted forward pass per chunk. Every transformer result recorded this session (Stage 1's seed7/13/42, Stage 2's in-progress run) is unaffected and stands as-is.
  - **Hybrid: real correctness impact.** GDN-2's recurrent state is never a tuple, so it was never reset by the `carry_attention_state=False` default -- every truncated-BPTT hybrid run this session (i.e. every hybrid run, since `chunk_length < sequence_length` was always used) computed its actual training loss and gradients against this wrong state. Training still visibly worked (loss decreased sensibly in every run, matching real learning dynamics) because the wrong state is a smoothly-related, plausible value, not garbage -- but it is not the value truncated-BPTT is supposed to use.
- **Fix:** `chunk_loss` now returns `(loss, next_state)` as an aux output (`mx.value_and_grad` only differentiates the first/scalar element of a returned tuple), so the correct post-chunk state comes free from the same forward pass already being computed for loss/grad -- the separate throwaway forward is gone entirely. Verified the fixed chunk0/chunk1 losses match the independently-computed correct values bit-for-bit.
- **Real throughput after the fix** (100K-token smoke runs, real 301M/302.6M topology, Stage-2 shape): hybrid **2,125 tok/s**, transformer **2,714 tok/s** -- both well above any number measured for the actual production loop all session, because the "Thermally-Honest Throughput Comparison" section above used a simplified profiling-script loss function that never had this bug and was therefore not a faithful proxy for the real training loop's prior throughput. Post-fix, the production loop is now structurally the same single-forward-per-chunk shape that benchmark measured, so its numbers should now be a much better proxy going forward.
- **Deliberately not done in this pass:** the "Replicated Stage 1 Signal" section elsewhere in this document and its hybrid-beats-transformer conclusion have NOT been edited, re-run, or caveated as part of this fix -- those runs used the buggy loop for hybrid specifically. Whether/how to re-verify that conclusion under the fixed loop is a separate, deliberately deferred decision, not resolved here.
- Full suite: 105/105 Python tests pass unchanged.

## Hybrid Forward-Path Cleanup: Real But Modest (2026-07-28)

- **Context:** while Stage 2's transformer phase trained (unaffected by anything here -- `CausalAttention` never touches `GDN2`), looked for real hybrid-specific inefficiency rather than guessing at one.
- **Found:** `GDN2` ran two separate `(dim, 3*dim)` Linear projections (`qkv`, `gates`) on the identical input every call, where `hz0a-pmetal-tensor`'s Rust `Gdn2Block` (already built and verified this session) uses one combined projection for the same computation -- the Python/MLX training path had drifted from that. Also, `Block.__call__`'s MLP computed `self.norm2(x)` twice (once per branch of the gate/up split) instead of once.
- **Fixed:** merged into one `(dim, 6*dim)` `self.in_proj`, weight/bias built as the literal concatenation of the old weights/biases -- mathematically guaranteed identical (a Linear over concatenated weight rows equals the two original Linears on the same input), verified bit-exact (`max diff 0.0`) against the old computation before committing, not just assumed. Deduplicated the `norm2(x)` call. Removed a redundant `if/else` in `Block.__call__` whose two branches were byte-for-byte identical code.
- **Verified:** all 105 Python tests pass unchanged, including the four that specifically compare native-Metal-kernel output against the pure-MLX reference recurrence (would have caught any channel-ordering mistake in the merge).
- **Honest sizing:** informal before/after profiling, taken under live GPU contention from the concurrent transformer training run (not a clean isolated measurement), showed a modest, noisy improvement -- forward `294->289ms`, backward `629->584ms`, roughly 4-7%. This is real (fewer kernel dispatches for identical FLOPs, can't make things worse) but small, and does not meaningfully close the ~1.65x gap the thermal benchmark measured cleanly above. Backward remains roughly 2x forward's cost even after this fix, which looks architectural (GDN-2's inherently more sequential per-timestep recurrence versus attention's more parallelizable matmul backward), not an obvious remaining bug. `mx.compile`-ing the full training step remains a real, larger, unattempted opportunity -- not attempted now given the risk of a broader untested change while a multi-hour Stage 2 run is live.
- **Breaking change, disclosed:** old hybrid checkpoints (including the existing Stage 1 seed7/13/42 runs) cannot be `--resume`d under this new parameter layout (`qkv.weight`/`gates.weight` -> `in_proj.weight`, same total parameter count, different structure). Safe right now only because Stage 2's hybrid phase hadn't started yet and launches fresh, not resumed.

## Thermally-Honest Throughput Comparison (2026-07-28)

- **Why this was needed:** cold-start GPU throughput bursts (~2.6k tok/s observed earlier this session) are not sustainable; steady-state after sustained load is lower. Any single-shot "hybrid does X tok/s, transformer does Y tok/s" number is confounded by which architecture happened to run first (cold GPU) versus second (already-hot GPU). New `scripts/hz0a_thermal_benchmark.py` removes that confound by alternating architectures and pooling both architectures' cold and hot slots symmetrically: `hybrid (cold) -> transformer (hot, inherits hybrid's heat) -> 90s cooldown -> transformer (warm-restart) -> hybrid (hot, inherits transformer's heat)`. Each architecture ends up with one cold-ish and one hot phase; the first 30% of steps in every phase are excluded from steady-state statistics so a phase's own internal ramp-up can't skew its own median.
- **Config:** locked 301M/302.6M topology, batch 2 x sequence 256 x chunk 128, 150 steps per phase (105 steady-state steps after the 30% ramp exclusion), native Metal GDN-2 kernel with the fused backward from the section below already in place. Full report: `outputs/hz0a_thermal_benchmark.json`.
- **Result: the transformer baseline is consistently, honestly faster than the hybrid at Stage-1-scale training throughput, in every one of its four measured phases, regardless of thermal ordering:**

| Phase | Architecture | Steady-state median tok/s | p10 | p90 |
| --- | --- | --- | --- | --- |
| 1 (cold) | hybrid | 1,055.6 | 1,050.7 | 1,060.5 |
| 2 (hot, after hybrid) | transformer | 1,911.8 | 1,878.2 | 1,946.7 |
| 3 (warm restart) | transformer | 1,569.6 | 1,549.4 | 1,589.1 |
| 4 (hot, after transformer) | hybrid | 940.1 | 908.5 | 964.0 |

  Pooled across both of its phases: hybrid **975.1 tok/s** median (p10 921.9, p90 1058.9), transformer **1,605.6 tok/s** median (p10 1555.8, p90 1939.9) -- transformer is **~1.65x faster** pooled, and the gap holds up in both individual head-to-head phase pairs (transformer beats hybrid whether hybrid goes first or transformer goes first). Peak memory: hybrid 5.80GB, transformer 6.16GB (hybrid is memory-cheaper, not just slower).
- **What this does and doesn't say:** this is a pure training-throughput comparison at Stage 1 scale on this specific hardware/kernel state, not a quality-per-wall-clock-hour comparison and not evidence about inference throughput (where the architectures' relative systems tradeoffs are expected to differ, per A12's long-context streaming-inference hypothesis, not yet tested). It also doesn't contradict the Stage 1 quality result below -- hybrid reaching a lower validation loss per *token* despite being slower per *second* are two separate, both-true claims that need to be reported together, not conflated into a single "hybrid is better" or "hybrid is worse" statement.

## Root-Cause Fix: Long-Sequence Metal Instability (2026-07-28)

- **Root cause found and fixed.** The `_SOURCE` forward kernel in `reference/hz0a_mlx_metal.py` was algorithmically broken: it recomputed the entire state history from scratch for every output timestep (O(S²) per thread), with an additional full recompute-and-sum over all K key channels specifically for `key == 0` threads producing the output (effectively O(S²·K) for those threads). The backward kernel (`_BACKWARD_BODY`) was already written correctly as a single O(S) sequential scan; the forward kernel was never brought in line with it.
- At chunk_length=128 (the training default) this was slow but survived. At S=1024 (the un-chunked validation forward, and any single kernel call beyond ~128-256 tokens) the per-thread work exploded ~64x, and the call either hung or ran long enough to trip the OS/driver's GPU command-buffer watchdog — this is what earlier sessions observed and logged as a "GPU command-buffer recovery error." It was never a memory leak; active memory was flat in every prior log, consistent with a compute-bound stall rather than growth.
- **Direct repro before fix:** a bare 1024-token forward call on the locked 301M topology did not return within 100s (confirmed via `/tmp/test_full_fwd.py`, timeout at 100s with no output past model construction).
- **Fix:** rewrote `_SOURCE` to match the backward kernel's pattern — grid reduced from `B*H*V*K` to `B*H*V` threads, each thread holds a thread-local `state[64]` array and does a single O(S) forward pass accumulating state and emitting output per timestep, no recomputation. Updated `native_gdn2_forward`'s `grid`/`threadgroup` dispatch to match. Math verified equivalent to `_reference_forward` by hand (decay/erase indexed by key, write/value indexed by value channel, matching the einsum-style broadcast in the pure-MLX reference).
- **Same repro after fix:** identical 1024-token forward call completes in 0.53s (active 1.37GB, peak 2.93GB). All 10 existing MLX-metal/native-replay/benchmark/training-smoke tests still pass unchanged (`pytest tests/reference/test_hz0a_mlx_metal.py tests/reference/test_hz0a_mlx_native_replay.py tests/reference/test_hz0a_mlx_native_benchmark.py tests/reference/test_hz0a_mlx_training_smoke.py` — 10 passed).

Result: `budget_complete=True`, loss `10.55 -> 6.59-7.07`, finite throughout, peak memory bounded and nearly flat (`7.455GB -> 7.617GB` over the full run, a 2.2% drift from repeated checkpoint I/O, not unbounded growth), `348.4 tok/s`.
