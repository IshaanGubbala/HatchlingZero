# HZ-0A Checkpoint Audit — step 2153 — 2026-07-26

The user flagged a 3.5 GB safetensors checkpoint as suspiciously large for a
labeled 110M-parameter model. This is the audit's findings.

## TL;DR

The HZ-0A MLX Phase 14 run that completed at step 2153 with `train_loss=8.3960`
/ `val_loss=8.4351` and ~386 tok/s was **not a 110M-parameter model** as the
directory name `outputs/training/hz0a_110m/` suggests. The actual model is
~292 M parameters and is mislabeled by 2.66×. The PyTorch `.pt` checkpoint at
`outputs/hz0a-mac-110m-fair/step_0000325.pt` is, however, correctly sized at
**109.9M** — that's a separate, older run and confirms the project's
110M baseline architecture is real but lives under a different directory.

The `train_loss = 8.40 / val_loss = 8.43` numbers are honest — they reflect a
≈290M model, not a 110M model. Comparison to a properly-sized 110M baseline
will require either resizing this checkpoint or training a fresh 110M
configuration.

## Audit Method & Tool

A new permanent audit tool is at `scripts/audit_checkpoint.py`. It:

* Enumerates each safetensors key with shape, dtype, byte size.
* Splits keys structurally into **model vs. optimizer** buckets by top-level
  dotted-prefix (`opt.` for optimizer; `embedding`, `lm_head`, `norm*`,
  `layers` for model).
* Counts params per bucket, computes Adam state ratio (expect ≈ 2.0),
  detects content-duplicate keys, distinguishes **tied weights**
  (`embedding.weight ↔ lm_head.weight`) from real duplicate-content bugs.
* Compares **lower-bound param prediction** from `--expected-config` against
  observed (within ±20%).
* Compares **explicit `--expected-param-count-M`** against observed
  (within ±50%).
* `--auto-parse-dir-label` extracts the `(\d+(?:\.\d+)?)m` suffix from the
  parent directory name and uses it as the expected count — the project's
  actual concern is "directory name says 110M but the file is 3.5 GB".
* Always writes a sibling `*.audit.json` with `allow_nan=False`.

The audit's verdict for the current step is:

* `param_count_anomaly(actual=292.04M, claim=110.00M, ratio=2.656)` — **fails**.
* No `runtime_pollution` — every key is either `opt.*` or a known model layer
  prefix.
* No `duplicate_content_anomaly` — content hashes are unique.
* `optimizer_factor_vs_model = 2.0000` exactly, classifying the optimizer
  state as standard Adam (`m`, `v` per parameter + a single `opt.step`
  counter in uint64).

## PyTorch Cross-Check (`.pt`)

The PyTorch checkpoint at `outputs/hz0a-mac-110m-fair/step_0000325.pt` is a
**different run** from an earlier phase:

* `model_state_dict`: 293 keys
* Total params: **109,937,664** (≈ 109.94M), exactly matching the "110M" label.
* All `torch.float32`. Tensor-only bytes are ~419 MB; total on-disk size
  ~419 MB (essentially the same; `.pt` ZIP overhead is small at this
  parameter count).
* Keys match expected HZ-0A GDN2 hybrid architecture
  (`token_emb.weight`, `layers.0.mixer.in_proj.weight`, …).

This confirms the project HAS a real 110M model — it just isn't the one that
ran in Phase 14. Phase 14 trained a ~290M model under a directory name that
suggested 110M.

## Implications

1. **The completed Phase 14 loss numbers are honest for a 290M model.**
   No contamination, no optimizer pollution. Step 2153 represents a valid
   ~290M HZ-0A hybrid loss trajectory.

2. **The "110M" label is misleading.** Anyone who later compares this
   checkpoint's loss against a properly-sized 110M baseline will see an
   artificially large advantage generated by the size difference (≈2.66× more
   parameters, not architecture quality).

3. **Directory rename is required before any downstream 110M-vs-X comparison.**
   Either:
   * Move `outputs/training/hz0a_110m/` → `outputs/training/hz0a_300m/` and
     update the dashboard / config references, **or**
   * Train a fresh Phase 14 run with the smaller configuration (768 hidden
     dim, ~12 layers, ~8 heads) that yields ~110M params, and use that as the
     110M baseline.

4. **The fused-Metal replay and the `phase14_fused` plan need clarification.**
   The chunked-VJP A/B replay needs to load a 290M checkpoint, not a 110M
   one, and any "end-to-end speedup" claims should be measured against this
   actual size.

## Recommended Next Steps

* **[Immediate] Rename or relabel**: pick one of the two strategies above.
* **[Pre-launch gate] Chunked-VJP A/B replay** (100–200 optimizer steps at the
  actual 290M scale) — does fused-Metal preserve the loss/gradient/parameter
  dynamics that produced step-2153 finetune results?
* **[Comparison gate] Fresh 110M-cap training run** with identical token budget
  (4.09M tokens, batch size, gradient accumulation, LR schedule) so the
  110M-vs-290M comparison is honest.
* **[Audit improvement] Audit script should read `kind.txt` sidecar**
  to distinguish full vs model_only checkpoints and adjust the
  `optimizer_type_mismatch` verdict accordingly (otherwise half the
  checkpoints give false-positive verdicts).

## Reproducing this Audit

```bash
./.venv/bin/python scripts/audit_checkpoint.py \
    outputs/training/hz0a_110m/step_0002153.safetensors \
    --expected-param-count-M 110

./.venv/bin/python scripts/audit_checkpoint.py \
    outputs/training/hz0a_110m/step_0002153.safetensors \
    --auto-parse-dir-label

./.venv/bin/python scripts/audit_checkpoint.py \
    outputs/training/hz0a_110m/step_0002153.safetensors \
    --expected-dim 768 --expected-layers 24 --expected-heads 12 \
    --expected-vocab 24000
```

All three modes flag the `param_count_anomaly` for this checkpoint. The
`.audit.json` sidecar at
`outputs/training/hz0a_110m/step_0002153.safetensors.audit.json` has the
full machine-readable verdict.
